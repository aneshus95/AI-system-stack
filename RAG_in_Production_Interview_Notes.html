2. Design decisions

Parsing and ingestion reliability

Bad extraction means bad chunks; better embeddings can't recover text that was never extracted.

  • Format-specific parsers, OCR for scans
  • Keep metadata: doc ID, page, tenant, permissions
  • Idempotent reprocessing, change detection
  • Queue + workers + retries + dead-letter queue + status table
Chunking strategy

Rule and its exception split across chunks gives a misleading answer.

StrategyProCon
Fixed sizeSimpleSplits ideas
RecursiveRespects boundariesUneven
Structure-awareHeadings, tables intactPer-doc logic
SemanticMeaning-basedCostly
Parent-childSearch small, return bigExtra storage

Small = precise but thin. Large = rich but noisy and costly. Overlap protects boundaries but duplicates. Start structure-aware or recursive, then test sizes on real questions.

Embedding model

Benchmark on your own query→relevant-doc set (domain, language, latency, price). Version model + preprocessing. Never mix vectors from different embedding spaces in one index; re-embed on incompatible upgrades.

Vector store choice

pgvector (existing relational data), managed vector DB (less ops), or a search engine (hybrid + rich filters). Judge by recall at target latency, filter speed, update time, concurrency, backups, cost. ANN can miss true neighbors, so tune the recall–latency trade-off.

3. Retrieval quality

If the evidence never reaches the LLM, it can't answer from it. Retrieval is the usual culprit.

DenseKeyword (BM25)
StrongMeaning, paraphraseIDs, rare terms
WeakExact identifiersSynonyms
FailureSimilar but wrong docDifferent vocabulary
Hybrid retrieval with RRF

Dense order: A B C D E. BM25 order: C A F B G. Raw scores aren't comparable, so fuse ranks: score = Σ 1/(k + rank).

C and A win because both retrievers like them. Lower k rewards top ranks more strongly.

The funnel
Index: millions of chunks
Retrieve: top 50 candidates
Rerank (cross-encoder): reorder
Filter + token budget: best 5–8
LLM

Candidate K ≠ final context K. Numbers are starting points; tune on labeled queries. Add a reranker when relevant docs are in the candidates but ranked low.

🔒
Access control: filter by tenant and permissions in a trusted backend before content reaches the model. The LLM is never the security boundary.

4. Generation

  • Token budget: instructions + history + question + context + output reserve ≤ window. Dedupe, prioritize authoritative sources, keep source IDs.
  • Grounded prompt: treat references as untrusted data, don't invent, say when evidence is insufficient, cite IDs, flag conflicts.
  • Citation checks: structural (ID exists), provenance (real doc + location), support (passage actually backs the claim). Citation markers ≠ grounded.
  • Abstain when evidence is missing or outdated: answer from the current doc, say it can't be established, ask a question, or escalate. Similarity scores aren't calibrated probabilities.

5. Evaluation

Evaluate retrieval and generation separately. Build a labeled set: question, expected facts, relevant doc IDs, answerable or not, tenant scope. Keep a held-out split.

Quality: recall on labeled samples, groundedness, citations, abstention, feedback. Latency: p50/p95/p99, TTFT, per-stage. Reliability: errors, timeouts, queue depth, index freshness. Cost: tokens, reranker calls, cost per successful answer.

7. Scaling to millions

"FastAPI with async" is not a scaling strategy.

 LB / Gateway ─► stateless RAG API replicas ─┬─► Retrieval svc (vector + keyword)
                                             └─► Model svc (embed / rerank / LLM)
 Queue ─► ingestion workers (parse → chunk → embed → index)
🚰
Analogy: 5,000 req/s into a provider that allows 500 req/s is a fire hose into a garden tap. More replicas won't help; you need backpressure.
  • Bounded concurrency, per-user and global rate limits, queues
  • Timeouts, cancellation, retries with backoff + jitter (no retry storms)
  • Circuit breakers, load shedding, provider quotas
Little's Law: L = λ × W
Requests in flight:

In-flight ≠ instances needed. One instance handles many I/O-bound requests; load-test to size replicas.

Ingestion at scale
Durable queue, idempotent jobs, batched embeddings, incremental indexing, dead-letter handling, backpressure, reconciliation jobs. Don't rebuild the whole index per update.

8. Freshness, versioning, security, cost

Safe document updates and deletes

Detect change → parse → embed → write new chunks → verify → make queryable → retire old. Consider building a new index version and switching traffic after validation.

Deleting a source file doesn't remove its chunks. Keep source → version → chunk ID maps. Permission revocations can't wait on eventual cleanup; enforce current auth at query time.

Version everything
Embedding model, preprocessing, index, chunking, retriever/reranker config, prompt, LLM and settings. Run regression tests on prompt changes.
Security risks → mitigations
  • Cross-tenant leakage → server-side tenant filters
  • Prompt injection in documents → treat as data, least-privilege tools, authorization outside the model, adversarial tests
  • PII in logs → minimize, redact, restrict
  • Malicious files → validate, sandbox parsers, resource limits
Cost optimization order
  1. Measure cost per request and per successful answer
  2. Cut duplicate and irrelevant context
  3. Tighten token budgets
  4. Cache where freshness and auth allow
  5. Smaller models for easy tasks; batch embeddings
  6. Re-evaluate quality after every saving

9. Releasing safely

 offline regression ─► staging ─► canary (small %) ─► compare live metrics ─► expand
                                                           └─ regression? roll back

Versioned indexes and configs make rollback easy. A/B tests need enough traffic; otherwise use offline eval + reviewed canaries.

10. The 60-second answer

How would you build RAG in production?

Ingestion: async, idempotent pipeline: parse, chunk, keep metadata and permissions, embed, index; handle retries, updates, deletes.

Retrieval: dense baseline, evaluate on a labeled set; add BM25 hybrid if exact terms matter; measure Recall@K; add a reranker if relevant docs rank too low.

Generation: token-budgeted evidence, grounded prompt, validated citations, abstain when evidence is thin.

Evaluation: separate retrieval and answer metrics; human review on high-risk cases.

Operations: tracing, p95 latency, cost, freshness; timeouts, bounded concurrency, backpressure; access control and injection defenses; canary releases.

Principle: optimize measured failure modes; don't add complexity by default.
